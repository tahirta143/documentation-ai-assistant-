# Documentation Assistant Test Document

## Introduction
This document is used to test the chunking pipeline of the documentation assistant system.
It contains multiple sections with enough text to produce several chunks when processed.

## Section 1: Architecture Overview
The documentation assistant uses a Retrieval-Augmented Generation (RAG) architecture.
RAG systems combine the power of large language models with the precision of information retrieval.
The system works by first ingesting documents, splitting them into chunks, embedding those chunks
into a vector space, and then at query time retrieving the most relevant chunks to provide context
to the language model when generating answers.

## Section 2: Document Processing Pipeline
When a document is uploaded to the system, it goes through several processing stages.
First, the raw file is saved to disk and a record is created in the database with a status of
processing. Next, the text extraction phase reads the file and converts it to plain text,
handling different formats like PDF, Markdown, and plain text files appropriately.
After extraction, the text cleaning phase normalizes whitespace, removes control characters,
and handles unicode normalization to ensure consistent text quality.

## Section 3: Chunking Strategy
The chunking phase splits the cleaned text into overlapping windows of tokens.
Using token-based chunking rather than character-based chunking ensures that each chunk
fits consistently within the embedding model's context window.
The default configuration uses chunks of 800 tokens with an overlap of 100 tokens.
This overlap ensures that information at chunk boundaries is not lost and that
semantic coherence is maintained across consecutive chunks.

## Section 4: Embedding and Retrieval
After chunking, each chunk is sent to the embedding model to generate a high-dimensional
vector representation of its semantic content. These vectors are stored in PostgreSQL using
the pgvector extension, which provides efficient similarity search capabilities.
At query time, the user's question is also embedded and compared against stored chunk embeddings
using cosine similarity to find the most semantically relevant chunks.

## Section 5: Answer Generation
The top-K most relevant chunks are assembled into a context block and passed to the language
model along with the user's question and a system prompt that instructs the model to answer
only using the provided context. This grounding ensures the model does not hallucinate
information that is not present in the uploaded documentation.
The response is returned to the user along with source citations identifying which documents
and pages the answer was drawn from.

## Section 6: Database Schema
The system uses five main tables: users, documents, document_chunks, conversations, and messages.
The document_chunks table includes a vector column of dimension 1536 which stores the embedding
for each chunk. An IVFFlat index on this column enables fast approximate nearest neighbor search.
The messages table includes a JSONB sources column that stores citation metadata for each
assistant response, allowing the frontend to display source references to users.

## Conclusion
This test document contains sufficient text to verify that the chunking pipeline correctly
splits content into multiple overlapping chunks and stores them in the database.
A successful test will show multiple rows in the document_chunks table after this file is uploaded.
